# CryptoAnalysis — заметки для Claude

Сайт прогнозов для криптовалют (Next.js 15 + MariaDB). Прогноз собирается из обученной модели
(`services/predictor`, модели в `models/predictor`), LLM через OpenRouter и правил
(`services/ensemble-prediction.ts`). Торговый бот и исследовательские модули лежат в `archive/`:
их не собирают и не выкладывают.

Пользователь не разбирается в git: коммиты, ветки и PR делаешь ты, а от него нужны только
понятные шаги на русском.

## Проверка перед PR

```bash
npm ci
npm test          # vitest
npm run build     # тот же тайпчек и линт, что в CI
```

CI (`.github/workflows/ci.yml`) гоняет тесты с MySQL и сборку на каждый PR и push в `main`.

## Параллельная работа нескольких сессий

Над репозиторием одновременно работают облачная сессия Claude и локальная сессия на ПК пользователя.

- **Никогда не пушить в `main` напрямую.** Одна задача = одна ветка `claude/<тема>` от свежего
  `origin/main` = один PR. Вливает пользователь после зелёного CI.
- Перед началом работы и перед PR подтягивать `origin/main`; конфликты решать в своей ветке.
- **`deploy/` и `.github/workflows/` меняет только локальная сессия**: у неё есть SSH к серверу
  и она проверяет каждое изменение выкладки на живой машине. Если облачной сессии что-то нужно
  в выкладке (новая переменная окружения, сервис, cron), опиши это в описании PR, а не меняй
  скрипты сам.
- Новые переменные окружения добавлять в `.env.example`. Если значение нужно на сервере,
  сказать об этом в PR.

## Сервер (прод)

Два сервера. Облачная сессия SSH-доступа не имеет. **Репозиторий публичный:** адрес, назначение и
соседние сервисы сервера-бэкенда в репозиторий не писать (ни в код, ни в документацию, ни в коммиты) —
они есть только в `.env` серверов и в локальных заметках сессии.

- **Бэкенд** — закрытый сервер владельца: здесь работает всё (сайт, база, бот, сбор данных). Файрвол
  закрыт для интернета и пускает только фронт; рядом работают важные сервисы владельца — их не трогать,
  портов наружу не открывать, память общая (сборка в группе памяти до 1,3 ГБ, сервисы с `MemoryMax`).
- **Фронт `83.222.16.56`** (Ubuntu 24.04, 1,9 ГБ + 2 ГБ swap) — только вход: его Caddy отдаёт
  `https://83.222.16.56:8443` и пересылает на бэкенд по TLS (`deploy/front-proxy.sh`). Старая копия
  сайта на нём остановлена.

| Что | Где |
|---|---|
| Сайт | `https://83.222.16.56:8443` → Caddy фронта → бэкенд; `SITE_PRIVATE=true`: только для вошедших, пользователей добавляет админ |
| Код | `/opt/cryptoanalysis` на бэкенде (git checkout `main`, владелец root) |
| Настройки | `/opt/cryptoanalysis/.env` (root:cryptoanalysis 640) |
| Сервис | `cryptoanalysis.service`, слушает `127.0.0.1:3101`, `MemoryMax=700M` |
| Модели | обучаются **только в GitHub Actions** (`.github/workflows/train-models.yml`, суббота) из архива `data.binance.vision`, релиз `models` (`candles-<tf>.json`, `pooled-<tf>.json`); сервер забирает их в `/opt/cryptoanalysis-data/models` таймером `cryptoanalysis-models-sync` (06:00). На сервере не обучать: 1,9 ГБ памяти на всё |
| Сбор данных | `cryptoanalysis-market-data.timer` каждые 5 минут, `MemoryMax=250M`; монеты: топ-40 + `POOLED_UNIVERSE` + все списки из Telegram |
| База | MariaDB, база и пользователь `cryptoanalysis`, только 127.0.0.1 |

**Соседи, которых нельзя задеть:** на фронте — `ase.service` (127.0.0.1:3000, `https://83.222.16.56` через
тот же Caddy), PostgreSQL 16, strongSwan; порты 80, 443 и 3000 заняты. На бэкенде — всё, что не наше:
перед любым изменением смотреть `ss -ltnp` и не занимать чужие порты.

### Стоимость сделок

Все расчёты прибыльности (лаборатория стратегий, `lib/trade-economics.ts`, исходы сигналов) используют одну модель
исполнения, `LAB_EXECUTION` / `tradeCost` в `services/strategy-lab/lab.ts`: вход рыночным ордером (0,05% +
проскальзывание 0,03%), цель — лимитным (0,02%), стоп и выход по времени — рыночным (0,05% + 0,03%). Сделка
считается прибыльной, только если она в плюсе при таком исполнении. Не возвращать «всё по цене закрытия с
комиссией лимитного ордера» — это завышало результат.

### Сигналы в Telegram и общая модель

- Бот управляется командами из подключённого чата (`services/signals/bot.ts`, long polling внутри сайта):
  `/watch`, `/unwatch`, `/list`, `/stats`, `/pause`, `/resume`, `/observe on|off`. Состояние хранится в MySQL
  (`services/signals/store.ts`): списки монет, журнал сигналов с реальными исходами.
- Сигнал отправляется, только если настройка сделок модели прибыльна после комиссий на отложенном периоде
  в целом **и на этой монете** (`coinVerdict`, `strategy.bySymbol`, от 10 проверочных сделок).
- Кроме проверенных сигналов бот шлёт **шансы** (`/observe`, включены по умолчанию): уверенная модель с подтверждённой
  точностью направления, план сделки с целью и стопом на равном расстоянии (`services/signals/chance.ts`), не больше
  одного открытого шанса на монету и пауза 4 ч после каждого (`CHANCE_COOLDOWN`). В каждом плане строка «не входить, если…»
  (`entryLimits`: цена прошла половину пути до цели или за стоп, прошла четверть срока, не меньше 5 мин). Сканер
  запускается через 20 с после каждой 5-минутной отметки (`msToNextScan`), сразу после закрытия свечей. Сильные новости приходят с таким же планом. Всё пишется в `signal_log` с полем
  `kind` (`signal`, `chance`, `news`) и закрывается по цели, стопу или времени; `/stats` и вкладка «Сигналы»
  считают виды отдельно.
- Каждая отправленная возможность — карточка на сайте: вкладка «Возможности» и `/opportunities/<id>`
  (`services/opportunities/card.ts`, `/api/opportunities`). В `signal_log.details` хранится, почему она отправлена;
  сведения о монете и свечи для графика берутся живыми при открытии. Ссылку на карточку бот добавляет в сообщение,
  только если задан `SITE_URL` (на сервере `https://83.222.16.56:8443`).
- Модель отключается сама, если после 30 реальных сигналов её средний результат после комиссий отрицательный. Считаются только
  `kind = 'signal'`: шансы и новости с самого начала помечены как непроверенные.
  Включается снова после переобучения (новый `trainedAt`).
- Общая модель (`services/pooled`): свечи + открытый интерес, лонг/шорт, тейкеры, фандинг, ~30 монет, 1h и 4h.
  Обучение — из архива `data.binance.vision` (из GitHub Actions Binance API недоступен, архив — доступен); в
  работе те же ряды берутся из таблиц сборщика. Правила выравнивания (`alignDerivs`) общие для обучения и работы:
  менять их можно только вместе с переобучением.

### Подписка и оплата

- Бесплатно: 1 прогноз анониму, 3 после регистрации (`lib/quota-config.ts`). Платный доступ (`hasPaidAccess`): админ,
  бессрочный `tier = 'paid'` (выдаётся вручную) или `users.paid_until` в будущем.
- Оплата — USDT (TRC20) прямо на кошелёк владельца, без платёжного сервиса (`services/payments`). Счёт получает
  уникальную сумму (цена + 1–99 центов), сайт раз в 30 с ищет подтверждённые переводы через TronGrid и продлевает
  подписку на `PAYMENT_PERIOD_DAYS`. Перевод засчитывается до суток после истечения счёта, одна транзакция — один счёт.
  Без `PAYMENT_USDT_TRC20_ADDRESS` окно оплаты пишет «скоро будет доступна». Ошибочный перевод админ закрывает
  вручную кнопкой «+30 дней» в `/admin`.
- Без подписки во «Возможностях» видны только закрытые сделки; идущие и их карточки — по подписке.

### Новые монеты на OKX

`services/listings` — монитор внутри сайта, раз в 5 минут (`LISTINGS_MONITOR=false` выключает): анонсы листингов
OKX, монеты, впервые появившиеся на OKX (только `instCategory=1`, криптовалюты; акции и pre-IPO отсеиваются), сводка
(Binance, CoinGecko), часовые свечи первых 7 дней в MySQL (`listing_coin`, `listing_bars`, `listing_announcement`).
История — монеты за 2 года, пополняется по 12 монет за цикл. Статистика и проверка вариантов сделок — в
`services/listings/analysis.ts`: подбор на ранних 60% листингов, проверка на поздних, стоимость с проскальзыванием 0,2%.
Снятых с торгов монет OKX не отдаёт — это надо помнить, читая статистику покупок.

### Сеть и VPN

С бэкенда OpenRouter и Telegram доступны напрямую: `OUTBOUND_SOURCE_IP` там пустой. Ниже — как это
устроено, когда сайт работает на российском сервере (код остался).

Из РФ OpenRouter отвечает **403**, а Binance и OKX доступны напрямую. VPN здесь — **IPsec-туннель
(strongSwan), а не прокси**: через туннель уходят только пакеты с адресом-источником `10.77.77.1`.
`deploy/install.sh` находит этот адрес (`OUTBOUND_SOURCE_IP`), а `lib/outbound-proxy.ts` подменяет
глобальный HTTPS-агент Node так, что к этому адресу привязываются только соединения с хостами из
`OUTBOUND_VPN_HOSTS` (по умолчанию `openrouter.ai` и `api.telegram.org`). Через туннель запрос идёт ~2 с вместо ~0,4 с,
поэтому Binance, CoinGecko и остальное ходят напрямую. Отсюда правила:

- запросы к OpenRouter и Telegram делать через **axios или `https`** (они используют глобальный агент).
  Встроенный `fetch` (undici) агент не использует: с ним OpenRouter снова даст 403;
- `OUTBOUND_PROXY` на этом сервере не нужен: локального прокси здесь нет.
- Адрес туннеля может смениться при переподключении VPN: 29.09.2026 он стал `10.77.77.2` вместо `10.77.77.1`,
  и неделю ни одно сообщение бота не ушло (`bind EADDRNOTAVAIL`). Теперь `lib/outbound-proxy.ts` раз в минуту
  проверяет адреса интерфейсов и берёт другой адрес из той же /24, а `install.sh` переопределяет пропавший адрес.
  Сбой доставки виден на вкладке «Возможности» (`lib/telegram.ts`, `telegramHealth`).

### Выкладка

1. PR влит в `main` → CI зелёный.
2. GitHub на закрытый бэкенд не заходит: таймер `cryptoanalysis-autoupdate` (каждые 5 минут) сверяет
   `main` с установленной версией и, если проверка CI `test` по новому коммиту зелёная, запускает
   обновление (`AUTO_UPDATE=true` в `.env`). Журнал: `journalctl -u cryptoanalysis-autoupdate`.
3. Запускается `deploy/update.sh`: `git fetch` явного URL репозитория и `reset --hard`
   на `main`, неотслеживаемые файлы переносятся в `/opt/cryptoanalysis-stray-*`, дальше `deploy/install.sh`.
4. `install.sh` повторяемый: `.env` не перезаписывает (кроме `COOKIE_SECURE`), собирает сайт, перезапускает сервис, обновляет блок Caddy между маркерами
   `# >>> cryptoanalysis`.

Правила для изменений в выкладке:

- Сайт пишет только в `.next`, `.cache`, `data` и `PREDICTOR_MODELS_DIR`. Остальной код
  принадлежит root, иначе взломанный сервис мог бы подменить скрипты, которые root запускает при
  выкладке. Новые места записи во время работы — только внутри `.cache` или через переменную
  окружения с путём вне checkout.
- Сборка идёт на сервере с 1,9 ГБ памяти: не добавлять тяжёлые зависимости сборки и не
  поднимать лимиты памяти, не проверив `free -h`.
- Не открывать порт приложения наружу и не отключать `COOKIE_SECURE`: сайт работает только через https.
