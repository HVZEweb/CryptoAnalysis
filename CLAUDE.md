# CryptoAnalysis — заметки для Claude

Сайт прогнозов для криптовалют (Next.js 15 + MariaDB). Прогноз собирается из обученной модели
(`services/predictor`, модели в `models/predictor`), LLM через OpenRouter и правил
(`services/ensemble-prediction.ts`). Торговый бот и исследовательские модули лежат в `archive/`:
их не собирают и не выкладывают.

Пользователь не разбирается в git: коммиты, ветки и PR делаешь ты, а от него нужны только
понятные шаги на русском.

## Проверка перед PR

```bash
npm ci
npm test          # vitest
npm run build     # тот же тайпчек и линт, что в CI
```

CI (`.github/workflows/ci.yml`) гоняет тесты с MySQL и сборку на каждый PR и push в `main`.

## Параллельная работа нескольких сессий

Над репозиторием одновременно работают облачная сессия Claude и локальная сессия на ПК пользователя.

- **Никогда не пушить в `main` напрямую.** Одна задача = одна ветка `claude/<тема>` от свежего
  `origin/main` = один PR. Вливает пользователь после зелёного CI.
- Перед началом работы и перед PR подтягивать `origin/main`; конфликты решать в своей ветке.
- **`deploy/` и `.github/workflows/` меняет только локальная сессия**: у неё есть SSH к серверу
  и она проверяет каждое изменение выкладки на живой машине. Если облачной сессии что-то нужно
  в выкладке (новая переменная окружения, сервис, cron), опиши это в описании PR, а не меняй
  скрипты сам.
- Новые переменные окружения добавлять в `.env.example`. Если значение нужно на сервере,
  сказать об этом в PR.

### Стоимость сделок

Все расчёты прибыльности (лаборатория стратегий, `lib/trade-economics.ts`, исходы сигналов) используют одну модель
исполнения, `LAB_EXECUTION` / `tradeCost` в `services/strategy-lab/lab.ts`: вход рыночным ордером (0,05% +
проскальзывание 0,03%), цель — лимитным (0,02%), стоп и выход по времени — рыночным (0,05% + 0,03%). Сделка
считается прибыльной, только если она в плюсе при таком исполнении. Не возвращать «всё по цене закрытия с
комиссией лимитного ордера» — это завышало результат.

### Сигналы в Telegram и общая модель

- Бот управляется командами из подключённого чата (`services/signals/bot.ts`, long polling внутри сайта):
  `/watch`, `/unwatch`, `/list`, `/stats`, `/pause`, `/resume`, `/observe on|off`. Состояние хранится в MySQL
  (`services/signals/store.ts`): списки монет, журнал сигналов с реальными исходами.
- Сигнал отправляется, только если настройка сделок модели прибыльна после комиссий на отложенном периоде
  в целом **и на этой монете** (`coinVerdict`, `strategy.bySymbol`, от 10 проверочных сделок).
- Модель отключается сама, если после 30 реальных сигналов её средний результат после комиссий отрицательный.
  Включается снова после переобучения (новый `trainedAt`).
- Общая модель (`services/pooled`): свечи + открытый интерес, лонг/шорт, тейкеры, фандинг, ~30 монет, 1h и 4h.
  Обучение — из архива `data.binance.vision` (из GitHub Actions Binance API недоступен, архив — доступен); в
  работе те же ряды берутся из таблиц сборщика. Правила выравнивания (`alignDerivs`) общие для обучения и работы:
  менять их можно только вместе с переобучением.

### Сеть и VPN

Из РФ OpenRouter отвечает **403**, а Binance и OKX доступны напрямую. VPN здесь — **IPsec-туннель
(strongSwan), а не прокси**: через туннель уходят только пакеты с адресом-источником `10.77.77.1`.
`deploy/install.sh` находит этот адрес (`OUTBOUND_SOURCE_IP`), а `lib/outbound-proxy.ts` подменяет
глобальный HTTPS-агент Node так, что к этому адресу привязываются только соединения с хостами из
`OUTBOUND_VPN_HOSTS` (по умолчанию `openrouter.ai` и `api.telegram.org`). Через туннель запрос идёт ~2 с вместо ~0,4 с,
поэтому Binance, CoinGecko и остальное ходят напрямую. Отсюда правила:

- запросы к OpenRouter и Telegram делать через **axios или `https`** (они используют глобальный агент).
  Встроенный `fetch` (undici) агент не использует: с ним OpenRouter снова даст 403;
- `OUTBOUND_PROXY` на этом сервере не нужен: локального прокси здесь нет.

### Выкладка

1. PR влит в `main` → CI зелёный → `.github/workflows/deploy.yml`.
2. GitHub Actions заходит по SSH как **`deploy`**, не root. Ключ привязан принудительной командой
   к `/usr/local/sbin/cryptoanalysis-deploy`, и ничего другого этот ключ сделать не может.
3. На сервере запускается `deploy/update.sh`: `git fetch` явного URL репозитория и `reset --hard`
   на `main`, неотслеживаемые файлы переносятся в `/opt/cryptoanalysis-stray-*`, дальше `deploy/install.sh`.
4. `install.sh` повторяемый: `.env` не перезаписывает (кроме `OPENROUTER_API_KEY` из секрета GitHub
   и `COOKIE_SECURE`), собирает сайт, перезапускает сервис, обновляет блок Caddy между маркерами
   `# >>> cryptoanalysis`.

Правила для изменений в выкладке:

- Сайт пишет только в `.next`, `.cache`, `data` и `PREDICTOR_MODELS_DIR`. Остальной код
  принадлежит root, иначе взломанный сервис мог бы подменить скрипты, которые root запускает при
  выкладке. Новые места записи во время работы — только внутри `.cache` или через переменную
  окружения с путём вне checkout.
- Сборка идёт на сервере с 1,9 ГБ памяти: не добавлять тяжёлые зависимости сборки и не
  поднимать лимиты памяти, не проверив `free -h`.
- Не открывать порт приложения наружу и не отключать `COOKIE_SECURE`: сайт работает только через https.
